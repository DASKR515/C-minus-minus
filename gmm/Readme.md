# gmm (GHC C-- Manager) v4.0

> **Linux:** `ghc` and a C compiler (`gcc` or `clang`) must already be installed, or point gmm at your own with `GMM_GHC` / `GMM_CC`.
> **Windows:** `gmm` installs a missing toolchain itself on first run by downloading the official GHC bindist — no Chocolatey, no manual steps.

**A standalone toolchain, project builder, and runner for writing and compiling C-- (Cmm) without the GHC Haskell Runtime System.**

`gmm` wraps GHC's Cmm front-end and a plain system linker to produce native binaries that are free of the Haskell RTS — no `stg_*` symbols, no `libHSrts`, and no multi-megabyte "Hello World" binaries. It ships with `libgmm/`, a bundled standard-library layer (`stdc--.h v3.0.0`, `cmmath.h v1.0.4`, `ret.h`) embedded directly into the `gmm` binary and extracted automatically at runtime, requiring no manual installation or header configuration.

```bash
gmm -o app main.cmm
```

That's it. One binary, one command, no separate headers to manage.

# What is C-- (Cmm)?

C-- (pronounced "C minus minus", written as **Cmm** in GHC's own tooling) is a low-level, C-like programming language designed by Simon Peyton Jones and Norman Ramsey in the late 1990s. The original goal was ambitious: a **portable assembly language** — a common target that any high-level compiler could generate, and any code-generator backend could consume, without either side needing to know about the other.

That original, compiler-agnostic version of C-- never really took off outside its own research project (Quick C--, abandoned around 2013). What *did* survive is a fork of it: **Cmm**, the intermediate representation GHC uses internally to compile Haskell down to machine code. GHC turns Haskell into Core, then STG, then Cmm, and from Cmm it can generate native assembly directly, hand off to LLVM, or (historically) emit plain C.

A minimal Cmm program using `stdc--.h` v3.0.0 looks like this:

```c
#include "Cmm.h"
#include "stdc--.h"

section "data" {
    msg: bits8[] "Hello, World!\0";
}

export main;

main() {
    mout(msg "ptr");
    mexit(0);
}
```

A few things worth knowing if you've never seen Cmm before:

* **`section "data" { ... }`** declares static data — strings, constants — much like a `.data` section in assembly. `section "bss"` is available for zeroed storage.
* **Types are explicit bit widths**, not C-style `int`/`float`: `bits8`, `bits32`, `bits64`, `float64`, or the platform-native word size `W_`. There is no hidden implicit conversion.
* **`foreign "C" func(...)`** is how Cmm calls into the standard C ABI — this is the *only* way to reach libc functions like `puts`, `malloc`, or `sqrt`. Cmm has no built-in standard library of its own.
* **Declare external functions with `import "C" name;`** before calling them. Do **not** `#include` a C header: the Cmm parser would try to parse C prototypes as Cmm and fail. A header written for the *C* half of your project belongs on the C side, listed in `cfiles`.
* **No plain `return` from `main` the way you'd expect** — see the warning further down. Cmm's calling conventions were designed around GHC's own runtime, and `main()` is a special case.
* Cmm has no classes, no generics, no memory safety — it's intentionally close to assembly, just readable.

Cmm is normally *generated by GHC itself*, not written by hand. This project (and `gmm`) exists to make hand-written Cmm practical — usable as a small, C-like systems language in its own right, without requiring you to write any Haskell or drag in the Haskell Runtime System.

# Why gmm exists

C-- (Cmm) is the low-level intermediate language used internally by the Glasgow Haskell Compiler. It's a clean, C-like language — but writing it by hand and compiling it the "normal" way (`ghc -no-hs-main file.cmm -o app`) comes with a hidden cost: **GHC's linker drags in the Haskell Runtime System even if your program never touches Haskell.**

We measured this on `main.cmm` (`puts` / `mout`):

| Property | `ghc -no-hs-main … -o app` | `gmm -o app main.cmm` |
| --- | --- | --- |
| Binary size | ~1.5 MB | **12,640 bytes** |
| RTS symbols (`strings app \| grep -ci stg`) | dozens | **0** |
| Dynamic deps | `libgmp`, `libffi`, `libiconv`, … | `libm`, `libc` |

The gap doesn't shrink as the program grows — it widens. That's the RTS footprint scaling in, not the program itself.

## What's actually in that "hidden" weight

Inspecting a GHC-linked binary with `strings app | grep -i stg` turns up dozens of internal RTS symbols that have nothing to do with the program logic, for example:

```text
stg_stack_underflow_frame: unsupported register
stg_dead_thread entered!
stg_sig_install: bad spi
stg_ap_p_ret
...
```

And `readelf -d app | grep NEEDED` on a stock GHC build shows dynamic dependencies that a hand-written Cmm "Hello World" has no logical reason to need:

```text
libgmp.so
libffi.so
libiconv.so
```

None of this is used by the program. It's there because GHC's default *linking* behavior assumes every binary it produces might need the full Haskell runtime.

A second, more practical consequence: linking through GHC also means the RTS has to be **installable**. On a machine without `libgmp` development files, `ghc -no-hs-main main.cmm -o app` fails outright:

```text
/usr/bin/ld.bfd: cannot find -lgmp: No such file or directory
```

`gmm` never touches the RTS, so it has no such dependency.

## How gmm avoids it

`gmm` splits compilation and linking into two separate steps instead of letting `ghc` do both:

```bash
ghc -c -no-hs-main -I<libgmm-path> main.cmm -o main.o
cc main.o -o app -no-pie -lm -lc
```

Because `cc` has no notion of the Haskell RTS, it links only what the object file actually references. The result is a binary with the same behavior and none of the extra weight.

# Installation

## Linux

```bash
go build -o gmm .
sudo mv gmm /usr/local/bin/
```

Requirements:

* `ghc`
* `gcc` or `clang`

must be available in `PATH`.

## Windows

Build normally:

```powershell
go build -o gmm.exe .
```

On its first execution, `gmm` checks whether the required toolchains are installed.

If they are missing, `gmm` automatically downloads and unpacks the official GHC bindist into its installation directory (`Ghc/`), alongside a generated `sit.txt` that records the resolved tool paths.

> **Administrator privileges and an internet connection are required only during the first setup.**

After the initial installation completes successfully, `gmm` can be used normally without administrator privileges.

## Building every platform

```bash
./build.sh          # → dist/gmm-linux-amd64, dist/gmm-linux-arm64, dist/gmm-windows-amd64
```

`libgmm/` is embedded into the executable using Go's `embed` package and extracted automatically into a temporary directory at runtime. It is removed when the process exits.

## Environment variables

| Variable | Purpose |
| --- | --- |
| `GMM_HOME` | Installation directory that holds `Ghc/` and `sit.txt`. |
| `GMM_GHC` | Path to a `ghc` binary. Skips the bundled toolchain lookup entirely. |
| `GMM_CC` | Path to the C compiler driver used for assembling and linking. |
| `GMM_LLVM` | Path to the LLVM `opt` tool, used with `-llvm`. |

A `GMM_GHC` that does not point at an executable is a hard error rather than a silent fallback, so a typo can never quietly compile with a different compiler than you intended.

# Usage & Commands

```bash
USAGE:
  gmm [flags] <input.cmm> [extra_files.o/a / dynamic_libs.so...]
  gmm [flags] build | -b
  gmm [flags] bc | -bc
  gmm [flags] run | -r [executable]
  gmm [flags] br | -br
```

## Command Line Flags & Commands

| Flag / Command | Type | Description |
| --- | --- | --- |
| `-o <file>` | Flag | Output binary name. With no `-o`, the default is `a.out`. |
| `-o C="<target>"` | Flag | Output format. See [Targets](#targets) below. |
| `-I <path>` | Flag | Add an include directory for headers. Repeatable. |
| `-D <name[=val]>` | Flag | Define a preprocessor macro. Repeatable. |
| `-S` | Flag | Emit assembly (`.s`) instead of building an executable/library. |
| `-b`, `build` | Command/Flag | Build project using configuration from `conf.hmm`. |
| `-bc`, `bc` | Command/Flag | Build using `conf.hmm` and clean the `.o` files this run created. |
| `-r`, `-run`, `run` | Command/Flag | Run the output executable, or a named one. |
| `-br`, `br` | Command/Flag | Build using `conf.hmm` and immediately execute the binary. |
| `-libs <libs>` | Flag | Comma-separated system libraries or paths to link with. Repeatable. |
| `-keep-obj` | Flag | Keep intermediate object files (`.o`) after linking. |
| `-llvm` | Flag | Use the GHC LLVM backend (`-fllvm`) during C-- compilation. |
| `-rts` | Flag | Use GHC directly as the linker driver instead of `cc`. |
| `-v`, `-version` | Flag | Display version and developer information. |
| `-h`, `-help` | Flag | Display help message and exit. |

### Argument order

Flags may appear before or after the input file; both of these are equivalent:

```bash
gmm -o app -keep-obj main.cmm
gmm main.cmm -o app -keep-obj
```

The input is identified as the first argument ending in `.cmm`, so extra objects and libraries can be listed in either position:

```bash
gmm -o app helper.o main.cmm
gmm -o app main.cmm helper.o
```

`gmm -br` and `gmm -r NAME` propagate the built program's exit code, so they compose with shell scripts and CI.

## Targets

`-o C="<target>"` selects the output *format*. Each name names a concrete file type, so the name always matches what lands on disk:

| Target | Produces | Extension |
| --- | --- | --- |
| `native` | plain executable for this host (default) | none |
| `exe` | Windows PE executable | `.exe` |
| `dll` | Windows PE shared library | `.dll` |
| `linux` | Linux ELF executable | `.elf` |
| `so` | native shared object | `.so` |

Aliases: `host` → `native`, `windows`/`pe` → `exe`, `elf` → `linux`, `shared` → `so`.

Combine both `-o` forms to pick the format and the name:

```bash
gmm -o C="linux" -o app main.cmm      # → app.elf
gmm -o C="so" -o libapp main.cmm       # → libapp.so  (see note below)
```

> ⚠️ **gmm does not cross-compile.** The toolchain produces objects for its own platform, so requesting a target for another OS is refused with an explanation rather than silently emitting a host binary under a foreign name. On Linux, `-o C="exe"` and `-o C="dll"` will error; use `native` or `linux`.

> ⚠️ **`so` may require the LLVM backend.** GHC's native code generator does not always emit position-independent code, so a shared object that references static data can fail to link. When that happens, gmm reports it and suggests the fix:

```bash
gmm -llvm -o C="so" -o libapp main.cmm
```

# `conf.hmm` API Specification

`conf.hmm` is the project configuration file for `gmm`.

## Syntax Rules

* One `key = value` pair per line.
* Comments start with `#` or `;`. Blank lines are ignored.
* Whitespace around keys and values is optional.
* List values are comma-separated.
* Values may be quoted.

## Available Keys

| Key | Aliases | Description |
| --- | --- | --- |
| `input` | `src`, `source` | Primary Cmm source file. |
| `output` | `out`, `bin` | Output binary path. |
| `target` | `type`, `format` | Output format; see [Targets](#targets). |
| `cfiles` | `csources`, `csrc` | C sources to compile and link. |
| `includes` | `incdirs` | Header include directories. |
| `defines` | `defs` | Preprocessor macro definitions. |
| `libs` | `libraries` | Libraries to link with. |
| `objs` | `objects`, `extraobjs` | Pre-compiled objects or archives. |
| `keepobj` | `keep-obj` | `true`/`false`; keep generated `.o` files. |
| `emitasm` | `asm` | `true`/`false`; emit assembly instead of linking. |
| `llvm` | — | `true`/`false`; use the LLVM backend. |
| `rts` | — | `true`/`false`; link with GHC as the driver. |
| `run` | — | `true`/`false`; run the binary after building. |

Unknown keys are ignored, so a config written for a newer gmm still loads.

## Actual `conf.hmm` Example

```hmm
# Configuration for gmm build system

input  = main.cmm
output = app
target = native

cfiles   = helper.c
includes = ., include
defines  = DEBUG, LEVEL=2
libs     = m, pthread

keepobj = false
```

Add a line like `objs = linkL.o` when your build needs a pre-compiled object; every listed object must exist, and a missing one is reported by name rather than at link time.

`gmm` looks for `conf.hmm` next to the input file first, then in the current directory. Command-line flags override values from the file, and command-line values from multiple flags accumulate rather than overwrite.

# Example Usage

```c
#include "Cmm.h"
#include "stdc--.h"

section "data" {
    msg: bits8[] "Hi Jordan\0";
}

export main;

main() {
    mout(msg "ptr");
    mexit(0);
}
```

```bash
# Build and run
gmm -br
# Hi Jordan

```

Mixing in a C helper uses `import "C"`, not a C header include:

```c
#include "Cmm.h"
#include "stdc--.h"

import "C" helper_triple;

export main;

main() {
    bits32 r;
    (r) = foreign "C" helper_triple(14);
    moutf("helper_triple(14) = %d\n", r);
    mexit(0);
}
```

```hmm
input  = main.cmm
output = app
cfiles = helper.c
```

## gmm vs. plain ghc

| Feature | Plain `ghc` | `gmm 4.0` |
| --- | --- | --- |
| Standalone Cmm compilation | ✅ | ✅ |
| RTS-free native binaries | ❌ | ✅ |
| No RTS dev libraries required | ❌ | ✅ |
| Automatic header discovery | ❌ | ✅ |
| Embedded `stdc--.h` v3.0.0 | ❌ | ✅ |
| Embedded `cmmath.h` v1.0.4 | ❌ | ✅ |
| Project configuration (`conf.hmm`) | ❌ | ✅ |
| Integrated execution (`-r`, `-br`) | ❌ | ✅ |
| Exit code propagation | ❌ | ✅ |
| Scoped Obj cleanup (`-bc`) | ❌ | ✅ |
| Cross compilation | ❌ | ❌ (refuses, rather than lying) |
| Linux support | ✅ | ✅ |
| Windows support | ✅ | ✅ |
| Automatic toolchain installation | ❌ | ✅ (Windows) |
| One-command build & run | ❌ | ✅ |

> ⚠️ **Use `mexit(0);` or `foreign "C" exit(0);` to terminate `main()`, not `return (0);`.**
> A bare Cmm-level `return` from `main` follows GHC's STG calling convention, which expects a stack frame normally created by the Haskell RTS. Without that frame, the program may crash after producing the correct output. This behavior is inherited from GHC itself and is not specific to `gmm`.

> ⚠️ **`-llvm` and `-rts` depend on your installation.** `-llvm` needs LLVM tools matching the GHC version, and `-rts` needs the GHC RTS libraries (notably `libgmp`). Both report a clear error and a hint when the dependency is missing.

# Bundled Libraries (`libgmm/`)

| File | Version | Description |
| --- | --- | --- |
| `stdc--.h` | **v3.0.0** | Comprehensive Cmm standard library layer interfacing standard `libc` functions (`stdio`, `stdlib`, `string`, `time`, `threads`, `stdatomic`). |
| `cmmath.h` | **v1.0.4** | Native math interface for Cmm providing wrappers around standard `math.h`. |
| `ret.h` | — | Calling-convention macros used by `stdc--.h` for tail calls and returns. |

All files are embedded into the `gmm` executable and extracted automatically at runtime. `cmmath.c` is only compiled when your source includes `cmmath.h`, so programs that don't use math never pay for it.

---

# What gmm is *not*

* Not a new compiler front-end — parsing and code generation still come entirely from GHC.
* Not a replacement for GHC — GHC remains the compiler backend.
* Not a replacement for a native C compiler — final linking is still performed by the platform toolchain (`gcc`, `clang`, or system `cc`).
* Not a cross compiler — it builds for the platform its GHC targets, and refuses other targets.
* Not a guarantee that every dependency disappears — programs may still link additional system libraries they explicitly use (for example `pthread` or `m`).
