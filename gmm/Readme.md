# gmm (GHC C-- Manager) v3.0

> **Linux:** `ghc` and a C compiler (`gcc` or `clang`) must already be installed.
> **Windows:** `gmm` automatically installs missing toolchains (GHC 9.8.2 and Clang) through Chocolatey (`choco`) during its first run if they are not present.

**A standalone toolchain, project builder, and runner for writing and compiling C-- (Cmm) without the GHC Haskell Runtime System.**

`gmm` wraps GHC's Cmm front-end and a plain system linker to produce native binaries that are free of the Haskell RTS — no `stg_*` symbols, no `libHSrts`, and no multi-megabyte "Hello World" binaries. It ships with `libgmm/`, a bundled standard-library layer (`stdc--.h v2.0.0`, `cmmath.h`) embedded directly into the `gmm` binary and extracted automatically at runtime, requiring no manual installation or header configuration.

```bash
gmm -o app main.cmm

```

That's it. One binary, one command, no separate headers to manage.

# What is C-- (Cmm)?

C-- (pronounced "C minus minus", written as **Cmm** in GHC's own tooling) is a low-level, C-like programming language designed by Simon Peyton Jones and Norman Ramsey in the late 1990s. The original goal was ambitious: a **portable assembly language** — a common target that any high-level compiler could generate, and any code-generator backend could consume, without either side needing to know about the other.

That original, compiler-agnostic version of C-- never really took off outside its own research project (Quick C--, abandoned around 2013). What *did* survive is a fork of it: **Cmm**, the intermediate representation GHC uses internally to compile Haskell down to machine code. GHC turns Haskell into Core, then STG, then Cmm, and from Cmm it can generate native assembly directly, hand off to LLVM, or (historically) emit plain C.

A minimal Cmm program using `stdc--.h` v2.0.0 looks like this:

```c
#include "Cmm.h"
#include "stdc--.h"

section "data" {
    msg: bits8[] "Hello, World!\0";
}

export main;

main() {
    mout(msg "ptr");
    mexit(0);
}

```

A few things worth knowing if you've never seen Cmm before:

* **`section "data" { ... }`** declares static data — strings, constants — much like a `.data` section in assembly.
* **Types are explicit bit widths**, not C-style `int`/`float`: `bits8`, `bits32`, `bits64`, `float64`, or the platform-native word size `W_`. There is no hidden implicit conversion.
* **`foreign "C" func(...)`** is how Cmm calls into the standard C ABI — this is the *only* way to reach libc functions like `puts`, `malloc`, or `sqrt`. Cmm has no built-in standard library of its own.
* **No plain `return` from `main` the way you'd expect** — see the warning further down. Cmm's calling conventions were designed around GHC's own runtime, and `main()` is a special case.
* Cmm has no classes, no generics, no memory safety — it's intentionally close to assembly, just readable.

Cmm is normally *generated by GHC itself*, not written by hand. This project (and `gmm`) exists to make hand-written Cmm practical — usable as a small, C-like systems language in its own right, without requiring you to write any Haskell or drag in the Haskell Runtime System.

# Why gmm exists

C-- (Cmm) is the low-level intermediate language used internally by the Glasgow Haskell Compiler. It's a clean, C-like language — but writing it by hand and compiling it the "normal" way (`ghc -no-hs-main file.cmm -o app`) comes with a hidden cost: **GHC statically links the Haskell Runtime System into your binary even if your program never touches Haskell.**

We measured this directly.

## GHC vs gmm — binary size

| Program | `ghc -no-hs-main` | `gmm 3.0` | Difference |
| --- | --- | --- | --- |
| `main.cmm` (`puts` / `mout`) | 1,561,312 bytes | 5,768 bytes | **~270×** |
| `main.cmm` + `stdc--.h` v2.0.0 | 9.7 MB | 16 KB | **~620×** |

The gap doesn't shrink as the program grows — it widens. That's the RTS footprint scaling in, not the program itself.

## What's actually in that "hidden" weight

Inspecting a GHC-linked binary with `strings app | grep -i stg` turns up dozens of internal RTS symbols that have nothing to do with the program logic, for example:

```text
stg_stack_underflow_frame: unsupported register
stg_dead_thread entered!
stg_sig_install: bad spi
stg_ap_p_ret
...

```

And `readelf -d app | grep NEEDED` on a stock GHC build shows dynamic dependencies that a hand-written Cmm "Hello World" has no logical reason to need:

```text
libgmp.so
libffi.so
libiconv.so

```

None of this is used by the program. It's there because GHC's default *linking* behavior assumes every binary it produces might need the full Haskell runtime.

## How gmm avoids it

`gmm` splits compilation and linking into two separate steps instead of letting `ghc` do both:

```bash
ghc -c -no-hs-main -I<libgmm-path> main.cmm -o main.o
cc main.o -o app -lm -lc

```

Because `cc` has no notion of the Haskell RTS, it links only what the object file actually references. The result is a binary with the same behavior and none of the extra weight.

# Installation

## Linux

```bash
go build -o gmm main.go
sudo mv gmm /usr/local/bin/

```

Requirements:

* `ghc`
* `gcc` or `clang`

must be available in `PATH`.

---

## Windows

Build normally:

```powershell
go build -o gmm.exe main.go

```

On its first execution, `gmm` checks whether the required toolchains are installed.

If they are missing, `gmm` automatically downloads and installs them through **Chocolatey (`choco`)**.

> **Administrator privileges and an internet connection are required only during the first setup.**

After the initial installation completes successfully, `gmm` can be used normally without administrator privileges.

`libgmm/` (containing `stdc--.h` v2.0.0 and `cmmath.h`) is embedded into the executable using Go's `embed` package and extracted automatically into a temporary directory at runtime.

# Usage & Commands

```bash
USAGE:
  gmm [flags] <input.cmm> [extra_files.o/a / dynamic_libs.so...]
  gmm [flags] build | -b
  gmm [flags] bc | -bc
  gmm [flags] run | -r [executable]
  gmm [flags] br | -br

```

## Command Line Flags & Commands

| Flag / Command | Type | Description |
| --- | --- | --- |
| `-o <file>` | Flag | Specify output binary name (default: "a.out" or target in `conf.hmm`). |
| `-b`, `build` | Command/Flag | Build project using configuration from `conf.hmm`. |
| `-bc`, `bc` | Command/Flag | Build project using `conf.hmm` and clean newly created `.o` object files. |
| `-r`, `-run`, `run` | Command/Flag | Run executable (runs output specified or passed executable file). |
| `-br`, `br` | Command/Flag | Build project using `conf.hmm` and immediately execute binary. |
| `-libs <libs>` | Flag | Comma-separated list of additional system libraries or paths to link with. |
| `-keep-obj` | Flag | Keep intermediate object files (`.o`) after linking instead of deleting them. |
| `-llvm` | Flag | Use GHC LLVM backend (`-fllvm`) during C-- compilation. |
| `-rts` | Flag | Use GHC directly as the linker driver instead of system C compiler (`cc`). |
| `-v` | Flag | Display version and developer information. |
| `-h`, `-help` | Flag | Display help message and exit. |

# `conf.hmm` API Specification

`conf.hmm` is the project configuration file for `gmm`. It uses plain block functions without required indentation or spaces before lines.

## Syntax Rules

* Comments start with `#` or `//`.
* Blocks open with `function "name"` and close with `end`.
* Values inside blocks are written directly on a new line without spaces or tabs.

## Available Blocks

| Block Name | Usage | Description |
| --- | --- | --- |
| `function "main"` | `path/to/file.cmm` | Primary Cmm source file path. |
| `function "out"` | `path/to/binary` | Target executable binary path. |
| `function "C"` | `path/to/file.c` | C source files to compile and link. |
| `function "lib"` | `libname` or `-I/path` | Dynamic/static system libraries or header include flags. |
| `function "obj"` | `path/to/file.o` | Pre-compiled object files or archives (`.o` / `.a`). |
| `function "defines"` | `MACRO_NAME` | Preprocessor macro definitions (passed as `-D`). |
| `function "flags"` | `-flag` | Compiler build flags (`-llvm`, `-rts`, `-keep-obj`). |

## Actual `conf.hmm` Example

```hmm
# Configuration for gmm build system

function "main"
main.cmm
end

function "out"
app
end

function "C"
helper.c
end

function "lib"
-I/usr/include
pthread
end

function "obj"
linkL.o
end

function "defines"
DEBUG
end

function "flags"
-keep-obj
end

```

## gmm vs. plain ghc

| Feature | Plain `ghc` | `gmm 3.0` |
| --- | --- | --- |
| Standalone Cmm compilation | ✅ | ✅ |
| RTS-free native binaries | ❌ | ✅ |
| Automatic header discovery | ❌ | ✅ |
| Embedded `stdc--.h` v2.0.0 | ❌ | ✅ |
| Embedded `cmmath.h` | ❌ | ✅ |
| Project configuration (`conf.hmm`) | ❌ | ✅ |
| Integrated execution (`-r`, `-br`) | ❌ | ✅ |
| Dynamic Obj cleanup (`-bc`) | ❌ | ✅ |
| Linux support | ✅ | ✅ |
| Windows support | ✅ | ✅ |
| Automatic dependency installation | ❌ | ✅ (Windows) |
| One-command build & run | ❌ | ✅ |

> ⚠️ **Use `mexit(0);` or `foreign "C" exit(0);` to terminate `main()`, not `return (0);`.**
> A bare Cmm-level `return` from `main` follows GHC's STG calling convention, which expects a stack frame normally created by the Haskell RTS. Without that frame, the program may crash after producing the correct output. This behavior is inherited from GHC itself and is not specific to `gmm`.

# Bundled Libraries (`libgmm/`)

| File | Status | Description |
| --- | --- | --- |
| `stdc--.h` | **v2.0.0** | Comprehensive Cmm standard library layer interfacing standard `libc` functions (`stdio`, `stdlib`, `string`, `time`, `threads`, `stdatomic`). |
| `cmmath.h` | **v1.0.0** | Native math interface for Cmm providing wrappers around standard `math.h`. |

Both headers are embedded into the `gmm` executable and extracted automatically at runtime.

---

# What gmm is *not*

* Not a new compiler front-end — parsing and code generation still come entirely from GHC.
* Not a replacement for GHC — GHC remains the compiler backend.
* Not a replacement for a native C compiler — final linking is still performed by the platform toolchain (`gcc`, `clang`, or system `cc`).
* Not a guarantee that every dependency disappears — programs may still link additional system libraries they explicitly use (for example `pthread` or `m`).
